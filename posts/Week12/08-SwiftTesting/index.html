Overview

The Swift Testing open source project was released in 2024 as an updated, Swift-ready framework for performing functional testing in Swift. Note that performance and UI testing are not supported by Swift Testing and still require the XCTest style testing discussed earlier.

Swift Testing makes heavy use of Swift features such as Macros, Attributes, async/await, and more. The testing API has been massively streamlined compared to XCTest, and fits in well using many of the same techniques and paradigms you have encountered so far when learning about Swift. Let's look at things in a demo.

Tests and Test Suites

Tests are denote with an @Test attribute. Unlike XCTest, you don't need to prefix test methods with test; the attribute tips off the testing framework that this method contains test code. Tests can be async and they can also throw.

@Test
func validate() async throws {

}

If you need to access types defined in your main set of code, you can import that code using @testable:

import Testing
@testable import EPExampleApp

This exposes the code in your main project to the testing target.

If you have multiple, related tests, you can use the @Suite macro to put them into a Test Suite, but that isn't necessary! You can simply wrap them in a struct, for example, and the testing framework will automatically treat it as a suite. The @Suite attribute is only needed if you are doing something else like adding a description.

@Suite("Teacher tests") //not required, but presents a recognizable name in the test panel
struct SwiftTesting {

  @Test
  func myTest() async throws {
    ///.....
  }

  @Test
  func myTest2() async throws {
    ///.....
  }
}

Expectations

The #expect macro takes over the many permutations of XCTAssert. Any operator or syntax that can be used to generate a boolean can be used within the body of #expect.

@Test
func validate() async throws {

  #expect(teacher.isCurrentlyTeaching && (teacher.studentNames.count != 0))
  #expect(teacher2.isCurrentlyTeaching && (teacher2.studentNames.count != 0))
  #expect(teacher3.isCurrentlyTeaching && (teacher3.studentNames.count != 0))
}

Conditions

You may want to only have tests run when specific conditions are met. Some conditions are shown below:

@Test(.enabled(if:<CONDITION>))

@Test(.disabled("Due to known crash"))

@Test(.disabled("Due to known crash"), .bug("github.com/issues/1", "Crashes on startup"))

Comments such as those above are shown in your test reports so you can see exactly why a test was skipped.

Arguments

To test a variety of inputs, you may want to rerun a test over and over again. Luckily, tests can take parameters in their function signature and you can use the arguments parameter of the @Test attribute to pass them in. The testing framework then calls each argument in its own instance of the test, ensuring they will not conflict with each other. The results are also listed separately for each argument, so you can see if particular inputs fail.

@Test(arguments: [teacher, teacher2, teacher3])
func validateWithArgument(teacher: Teacher) async throws {
  #expect(teacher.isCurrentlyTeaching && (teacher.studentNames.count != 0))
}
